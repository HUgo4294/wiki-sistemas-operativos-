En la Unidad 3 vimos cómo sincronizar procesos con mutex, semáforos y monitores. Esa sincronización resuelve las condiciones de carrera, pero introduce un riesgo nuevo: que los procesos queden **esperándose unos a otros para siempre**. A ese fenómeno se le llama **interbloqueo** (*deadlock*).

---

## 1. Definición y casos de interbloqueo

Un conjunto de procesos está en **interbloqueo** cuando **cada proceso del conjunto espera un evento que solo puede ser provocado por otro proceso del mismo conjunto**. Como todos esperan, ninguno avanza y ninguno libera lo que otros necesitan.

<Aside type="note" title="Interbloqueo vs. inanición">
En la **inanición** (*starvation*) un proceso espera indefinidamente, pero el resto del sistema sigue avanzando (por ejemplo, un proceso de baja prioridad que nunca recibe CPU). En el **interbloqueo** todos los procesos involucrados están detenidos y ninguno podrá avanzar sin intervención externa.
</Aside>

### 1.1 Ejemplos cotidianos

| Situación | Recurso retenido | Recurso solicitado |
| --- | --- | --- |
| Dos autos en un puente de un solo carril, uno frente al otro | Su mitad del puente | La mitad del puente del otro auto |
| Cruce de cuatro calles donde cada auto bloquea al de al lado | La esquina que ocupa | La esquina siguiente |
| Dos personas con un solo cuchillo y un solo tenedor, cada una con uno y necesitando ambos | Un cubierto | El cubierto de la otra persona |

### 1.2 Ejemplos informáticos

1. **Dos hilos y dos mutex.** El hilo A toma el candado 1 y pide el 2. El hilo B toma el candado 2 y pide el 1.
2. **Base de datos.** La transacción T1 bloquea la fila X y quiere la fila Y. La transacción T2 bloquea la fila Y y quiere la fila X.
3. **Dispositivos.** El proceso P1 tiene la impresora y pide el escáner. El proceso P2 tiene el escáner y pide la impresora.
4. **Memoria.** Dos procesos han reservado parte de la memoria y ambos piden más, pero no queda memoria libre.

### 1.3 Un interbloqueo en código (Python)

```python
import threading
import time

candado_a = threading.Lock()
candado_b = threading.Lock()

def hilo_1():
    with candado_a:
        time.sleep(0.1)
        with candado_b:
            print("Hilo 1 terminó")

def hilo_2():
    with candado_b:
        time.sleep(0.1)
        with candado_a:
            print("Hilo 2 terminó")

t1 = threading.Thread(target=hilo_1)
t2 = threading.Thread(target=hilo_2)
t1.start()
t2.start()
t1.join()
t2.join()
```

Al ejecutar este programa puede producirse un interbloqueo: cada hilo retiene un candado y espera el otro.

## 2. Las cuatro condiciones de Coffman

En 1971, Coffman, Elphick y Shoshani describieron cuatro condiciones necesarias para que pueda ocurrir un interbloqueo. Deben cumplirse simultáneamente.

| # | Condición | Significado | Ejemplo |
| --- | --- | --- | --- |
| 1 | **Exclusión mutua** | Al menos un recurso no puede compartirse. | Un mutex o una impresora. |
| 2 | **Retención y espera** (*hold and wait*) | Un proceso retiene recursos mientras solicita otros. | El hilo 1 tiene A y espera B. |
| 3 | **No expropiación** (*no preemption*) | Los recursos no se retiran por la fuerza al proceso que los retiene. | Un hilo mantiene un mutex hasta liberarlo. |
| 4 | **Espera circular** | Existe una cadena cerrada de procesos que esperan recursos retenidos por otros. | P1 espera a P2 y P2 espera a P1. |

<Aside type="caution" title="Necesarias, no suficientes">
Que se cumplan las cuatro condiciones no siempre implica un interbloqueo. Si ocurre un interbloqueo, las cuatro condiciones están presentes.
</Aside>

## 3. Estrategias para tratar los interbloqueos

| Estrategia | Idea | Costo |
| --- | --- | --- |
| **Prevención** | Diseñar el sistema para que al menos una condición de Coffman sea imposible. | Puede reducir el paralelismo. |
| **Evitación** | Conceder recursos solo si el estado resultante es seguro. | Requiere conocer las necesidades máximas. |
| **Detección y recuperación** | Permitir el interbloqueo, detectarlo y resolverlo. | Consume recursos para detectar y recuperar. |
| **Ignorar (avestruz)** | Asumir que el interbloqueo es poco frecuente. | Existe el riesgo de que el sistema se cuelgue. |

---

## 4. Prevención de interbloqueos

Consiste en **negar al menos una de las cuatro condiciones** mediante reglas de diseño.

### 4.1 Negar la exclusión mutua

Hacer que los recursos sean compartibles cuando sea posible. Por ejemplo, los archivos de solo lectura pueden ser compartidos. Para algunos dispositivos, una técnica parcial es el *spooling*, mediante el cual los trabajos se envían a una cola.

### 4.2 Negar la retención y espera

Hay dos enfoques:

- **Solicitar todo al inicio:** el proceso solicita todos los recursos que necesitará antes de comenzar.
- **Liberar antes de pedir más:** el proceso libera los recursos que retiene antes de solicitar otros.

La desventaja es el menor aprovechamiento de los recursos y la posible inanición.

### 4.3 Negar la no expropiación

Si una solicitud no puede atenderse, se pueden retirar recursos al proceso y reiniciarlo cuando sea posible. Esta técnica funciona mejor con recursos cuyo estado se puede guardar y restaurar.

### 4.4 Negar la espera circular

Se asigna un número único a cada tipo de recurso y se obliga a solicitarlos siempre en orden creciente. Así se evita formar ciclos de espera.

```python
import threading

candado_a = threading.Lock()
candado_b = threading.Lock()

def hilo_1():
    with candado_a:
        with candado_b:
            print("Hilo 1 terminó")

def hilo_2():
    with candado_a:
        with candado_b:
            print("Hilo 2 terminó")

t1 = threading.Thread(target=hilo_1)
t2 = threading.Thread(target=hilo_2)
t1.start()
t2.start()
t1.join()
t2.join()
```

### 4.5 Resumen de la prevención

| Condición negada | Técnica | Principal inconveniente |
| --- | --- | --- |
| Exclusión mutua | Recursos compartibles, *spooling* | No aplica a muchos recursos. |
| Retención y espera | Pedir todo al inicio | Desperdicio de recursos. |
| No expropiación | Quitar recursos al proceso | No sirve para todos los recursos. |
| Espera circular | Orden total de recursos | Hay que respetar el orden. |

## 5. Evitación de interbloqueos

La **evitación** analiza cada solicitud y solo la concede si el sistema permanece en un **estado seguro**. Para ello, necesita conocer de antemano el máximo de recursos que cada proceso podría llegar a solicitar.

### 5.1 Estado seguro e inseguro

- **Estado seguro:** existe una secuencia segura de procesos que permite que todos terminen con los recursos disponibles y los que van liberando los procesos anteriores.
- **Estado inseguro:** no se puede garantizar que todos los procesos puedan terminar.

Un estado inseguro no significa necesariamente que ya exista un interbloqueo, pero podría conducir a él.

### 5.2 Algoritmo del Banquero

Para n procesos y m tipos de recursos se utilizan estas estructuras:

| Estructura | Tamaño | Significado |
| --- | --- | --- |
| `Available` | Vector de m | Recursos libres de cada tipo. |
| `Max` | Matriz n × m | Máximo que cada proceso podría necesitar. |
| `Allocation` | Matriz n × m | Recursos asignados actualmente. |
| `Need` | Matriz n × m | Recursos que aún puede solicitar: `Max - Allocation`. |

#### Algoritmo de seguridad

<Steps>

1. Inicializar `Work = Available` y `Finish[i] = false` para todos los procesos.
2. Buscar un proceso i con `Finish[i] = false` y `Need[i] ≤ Work`.
3. Si se encuentra, simular que termina: `Work = Work + Allocation[i]` y `Finish[i] = true`. Volver al paso 2.
4. Si todos los valores de `Finish` son verdaderos, el estado es seguro. De lo contrario, es inseguro.

</Steps>

#### Algoritmo de solicitud de recursos

<Steps>

1. Si `Request[i] ≤ Need[i]`, continuar. Si no, la solicitud excede el máximo declarado.
2. Si `Request[i] ≤ Available`, continuar. Si no, el proceso debe esperar.
3. Simular la asignación: restar `Request` de `Available` y sumarlo a `Allocation`; actualizar `Need`.
4. Ejecutar el algoritmo de seguridad. Si el estado resultante es seguro, conceder la solicitud. Si es inseguro, revertir la asignación y hacer esperar al proceso.

</Steps>

### 5.3 Ejemplo resuelto

Sistema con cinco procesos y tres tipos de recursos A, B y C. Hay 10, 5 y 7 instancias totales.

| Proceso | Allocation (A B C) | Max (A B C) | Need (A B C) |
| --- | --- | --- | --- |
| P0 | 0 1 0 | 7 5 3 | 7 4 3 |
| P1 | 2 0 0 | 3 2 2 | 1 2 2 |
| P2 | 3 0 2 | 9 0 2 | 6 0 0 |
| P3 | 2 1 1 | 2 2 2 | 0 1 1 |
| P4 | 0 0 2 | 4 3 3 | 4 3 1 |

`Available = (3, 3, 2)`.

Una secuencia segura es:

**⟨P1, P3, P4, P0, P2⟩**

Por tanto, el estado es seguro.

### 5.4 Implementación en Python

```python
def es_seguro(available, allocation, need):
    n, m = len(allocation), len(available)
    work = available[:]
    finish = [False] * n
    secuencia = []

    while len(secuencia) < n:
        encontrado = False

        for i in range(n):
            if not finish[i] and all(
                need[i][j] <= work[j] for j in range(m)
            ):
                for j in range(m):
                    work[j] += allocation[i][j]

                finish[i] = True
                secuencia.append(f"P{i}")
                encontrado = True
                break

        if not encontrado:
            return False, []

    return True, secuencia


available = [3, 3, 2]
allocation = [
    [0, 1, 0],
    [2, 0, 0],
    [3, 0, 2],
    [2, 1, 1],
    [0, 0, 2]
]
maximo = [
    [7, 5, 3],
    [3, 2, 2],
    [9, 0, 2],
    [2, 2, 2],
    [4, 3, 3]
]

need = [
    [maximo[i][j] - allocation[i][j] for j in range(3)]
    for i in range(5)
]

print(es_seguro(available, allocation, need))
```

### 5.5 Limitaciones del Banquero

- Exige conocer las necesidades máximas de antemano.
- Supone un número definido de procesos y recursos.
- Los procesos deben liberar los recursos en un tiempo finito.
- Debe analizarse el estado cada vez que se evalúa una solicitud.

## 6. Detección y recuperación

En este enfoque, el sistema permite que ocurra el interbloqueo, lo detecta y después intenta resolverlo.

### 6.1 Grafo de asignación de recursos (RAG)

El *Resource Allocation Graph* representa procesos, recursos y las relaciones entre ellos.

| Elemento | Notación | Significado |
| --- | --- | --- |
| Proceso | Círculo Pi | Un proceso. |
| Recurso | Rectángulo Rj | Un recurso y sus instancias. |
| Solicitud | Pi → Rj | El proceso espera el recurso. |
| Asignación | Rj → Pi | El recurso está asignado al proceso. |

Si cada recurso tiene una sola instancia, un ciclo indica un interbloqueo. Si existen varias instancias, un ciclo puede indicar la posibilidad de interbloqueo, pero no lo demuestra por sí solo.

### 6.2 Detección con un grafo de espera

Se eliminan los nodos de recursos y se conecta un proceso con el proceso que retiene el recurso que necesita. Si existe un ciclo en este grafo, hay interbloqueo cuando cada recurso tiene una sola instancia.

```python
def hay_ciclo(grafo):
    visitando = set()
    visitado = set()

    def dfs(nodo):
        if nodo in visitando:
            return True

        if nodo in visitado:
            return False

        visitando.add(nodo)

        for vecino in grafo.get(nodo, []):
            if dfs(vecino):
                return True

        visitando.remove(nodo)
        visitado.add(nodo)
        return False

    return any(dfs(nodo) for nodo in grafo if nodo not in visitado)


espera = {
    "P1": ["P2"],
    "P2": ["P3"],
    "P3": ["P1"],
    "P4": ["P1"]
}

print("Hay interbloqueo:", hay_ciclo(espera))
```

### 6.3 Detección con varias instancias por recurso

Se compara lo que los procesos solicitan actualmente con los recursos disponibles. Si ningún proceso pendiente puede terminar con los recursos disponibles y los que se liberarían, quedan procesos bloqueados.

### 6.4 ¿Cuándo ejecutar la detección?

- Cuando se rechaza una solicitud.
- Periódicamente.
- Cuando disminuye el uso de CPU y hay indicios de procesos bloqueados.

### 6.5 Recuperación

Hay dos grandes opciones:

**Terminación de procesos**

- Abortar todos los procesos interbloqueados.
- Abortar uno a uno hasta romper el ciclo.

**Expropiación de recursos**

- Elegir una víctima.
- Restaurar un estado anterior mediante *rollback* o reiniciar el proceso.
- Evitar que siempre se elija al mismo proceso como víctima.

## 7. El enfoque del avestruz

El **algoritmo del avestruz** (*ostrich algorithm*) consiste en ignorar el problema cuando se considera que el costo de resolverlo supera el riesgo de que ocurra.

### 7.1 ¿Por qué puede utilizarse?

| Argumento | Explicación |
| --- | --- |
| Frecuencia baja | Los interbloqueos pueden ser poco frecuentes en ciertas aplicaciones. |
| Costo de las alternativas | La prevención, evitación y detección pueden tener costos importantes. |
| Rendimiento | En algunos sistemas se priorizan la flexibilidad y el rendimiento. |
| Solución manual | En ocasiones se puede terminar un proceso bloqueado o reiniciar un servicio. |

### 7.2 Matices importantes

- Los sistemas operativos pueden utilizar mecanismos internos para prevenir o detectar determinados bloqueos.
- Los gestores de bases de datos pueden detectar interbloqueos entre transacciones y abortar una de ellas.
- En sistemas críticos se utilizan técnicas específicas para reducir el riesgo de interbloqueo.

### 7.3 Herramientas de diagnóstico en Linux

```bash
# Ver procesos en estado D
ps -eo pid,stat,wchan:32,cmd | awk '$2 ~ /D/'

# Ver los archivos abiertos por un proceso
lsof -p PID

# Consultar la pila de ejecución de un proceso
sudo cat /proc/PID/stack

# Esperar como máximo cinco segundos por un candado
flock -w 5 /tmp/mi.lock -c "echo tengo el candado"
```

## 8. Comparación final de estrategias

| Estrategia | Cuándo actúa | Información necesaria | Uso típico |
| --- | --- | --- | --- |
| Prevención | Durante el diseño | Reglas de adquisición de recursos | Orden de candados. |
| Evitación | En cada solicitud | Máximo por proceso | Algoritmo del Banquero. |
| Detección y recuperación | Periódicamente o ante eventos | Estado actual | Bases de datos y sistemas por lotes. |
| Avestruz | No actúa directamente | Ninguna | Casos donde se acepta el riesgo. |

## 10. Resumen de la unidad

- El **interbloqueo** es una espera permanente entre procesos que retienen y solicitan recursos.
- Requiere las **cuatro condiciones de Coffman**: exclusión mutua, retención y espera, no expropiación y espera circular.
- **Prevención:** negar al menos una condición.
- **Evitación:** mantener el sistema en un estado seguro con el algoritmo del Banquero.
- **Detección y recuperación:** buscar ciclos y resolver el bloqueo terminando procesos o recuperando recursos.
- **Avestruz:** ignorar el problema cuando el costo de tratarlo supera el riesgo aceptado.
